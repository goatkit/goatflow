# TrueNAS SCALE App Catalog — Requirements for Publishing GoatFlow

Researched 2026-09-02. All facts verified against the authoritative sources listed at the bottom.

## TL;DR

Since TrueNAS SCALE 24.10 (Electric Eel), the app platform moved from Kubernetes/Helm
charts to **Docker Compose-based catalogs**. The old iX Helm catalog
(`truenas/charts`) and the TrueCharts community catalog are both deprecated.

To get GoatFlow into the official app store you submit a PR to
**github.com/truenas/apps** targeting the **`community` train**, which renders into
the built-in catalog on every 24.10+ system and the public
**TrueNAS Apps Market** (apps.truenas.com). No application fee, no support contract,
no separate review pipeline — it's a normal open-source PR with CI.

## 1. Supported TrueNAS versions

- 24.10 (Electric Eel) and later use the Docker Compose app platform; 24.10.2.2+ is
  what current catalog entries require (per Apps Market listings).
- 25.04 (Bluefin) and 25.10 (Cuttlefish) carry the same catalog mechanism forward.
  Note: 25.10 enforces a `services:` key in custom YAML deployments.
- Apps run on the Docker engine, not k3s. An `ix-apps` dataset is auto-created to
  store catalog data, app metadata, and container state.
- Apps Market docs: https://apps.truenas.com/getting-started/app-storage

## 2. Catalog / repo structure (the "manifest schema")

The catalog repo is https://github.com/truenas/apps. Apps live under
`ix-dev/{train}/{app-name}/`. Trains: `community` (where third-party contributions
go — the only one we can target), `stable`, `enterprise`, `dev`, `test`.

Each app directory must contain:

| File | Purpose |
| --- | --- |
| `app.yaml` | App metadata (required) |
| `ix_values.yaml` | Static defaults, not user-exposed (required) |
| `questions.yaml` | UI form schema (required) |
| `templates/docker-compose.yaml` | Jinja2 template that renders the compose file (required) |
| `README.md` | Short title + description (required) |
| `templates/test_values/basic-values.yaml` | CI test scenario (required) |
| `item.yaml` | Auto-generated catalog entry — do not hand-edit |
| `app_migrations.yaml` + `migrations/` | Python migration scripts (optional, for breaking config changes) |

Only files under `ix-dev/` (or `library/`) may be modified; `trains/`,
`catalog.json`, etc. are auto-generated by CI.

## 3. app.yaml fields (manifest)

```yaml
app_version: 2.1.0            # upstream app version == container image tag
capabilities: []              # Linux caps; auto-generated by script
categories: [productivity]    # single best-fit category
date_added: '2026-09-02'
description: short one-liner
home: https://goatflow.example.com
host_mounts: []               # host paths needed (e.g. /dev, docker.sock)
icon: https://media.sys.truenas.net/apps/goatflow/icons/icon.png
keywords: [...]
lib_version: 2.x.x            # latest library version from /library/ (check at submit time)
lib_version_hash: ""          # auto-filled
maintainers:
  - email: dev@ixsystems.com
    name: truenas
    url: https://www.truenas.com
name: goatflow                # MUST match directory name, lowercase
run_as_context:               # uid/gid metadata (568/568 if any non-root user works)
  - description: "GoatFlow runs as any non-root user"
    gid: 568
    group_name: goatflow
    uid: 568
    user_name: goatflow
screenshots: []               # CDN URLs (reviewer uploads on PR)
sources: []                   # upstream source repos
title: GoatFlow
train: community              # MUST match parent dir
version: 1.0.0                # chart version; semver, bump on every change
```

Naming rules (apply to app name and install names): lowercase alphanumeric, may
contain hyphens but not as first/last char, must start with a letter.

## 4. questions.yaml (UI form schema)

Defines the wizard form. The library expects a fairly fixed group structure —
follow existing apps for the exact shape:

- Groups: `My App Configuration`, `User and Group Configuration`, `Network`,
  `Storage`, `Labels`, `Resources` (skip user/group if the app runs as one fixed uid).
- Schema types: `string`, `int`, `boolean`, `dict`, `list`, `uri`, `path`,
  `hostpath`, plus `cron`, `ipaddr`, `secret`.
- Key attributes: `required`, `default`, `min`/`max`, `min_length`/`max_length`,
  `enum`, `show_if` (conditional display), `private` (password masking),
  `hidden`, `subquestions`, `attrs` (for dicts), `items` (for lists).

## 5. Docker Compose constraints (templating)

The compose file is generated by a Jinja2 template
(`templates/docker-compose.yaml`) that calls the Python rendering library:

- `tpl.add_container(name, image_key)` → containers
- `app.add_port()`, `app.add_storage()`, `app.environment.add_env()`,
  `app.healthcheck.set_test("curl", {...})` (health check binary must exist in the
  image), `app.depends.add_dependency()`
- Prebuilt deps: `tpl.deps.postgres()`, `deps.redis()`, `deps.mariadb()`,
  `deps.perms()` (permission init container — standard pattern)
- `tpl.portals.add(port, scheme, path)` → "Portal" web-UI links in the UI
- Ends with `{{ tpl.render() | tojson }}`

Consequences for GoatFlow:
- Image keys in `ix_values.yaml` must end with `image`; ghcr preferred over docker.io.
- Non-SemVer upstream tags need a custom regex in `renovate-config.js` for bot updates.
- Health check: ensure the container image ships the binary used (e.g. `curl`).
- Multi-service stacks (app + Postgres + etc.) are fine — this is compose.
- GPU passthrough: follow `plex`/`jellyfin` examples (device mappings + capabilities).

## 6. Port & volume conventions

- Ports are defined in `questions.yaml` as dict questions with `port` (int,
  min 1024, max 65535) and `bind_mode` (`published` or `host_network`); default
  ports should be picked to avoid common collisions; CI has a port-uniqueness
  validator (`.github/scripts/port_validation.py`).
- Storage: default to `ix_volume` (TrueNAS-managed dataset) with `host_path` as an
  alternative; use `show_if` to toggle the relevant sub-config.
- Test files mount under `/opt/tests/**` (macOS Docker whitelist + safety).

## 7. Licensing & support expectations

- The catalog repo itself is LGPL-3.0, but that governs the chart/metadata files,
  not your application code — your upstream license (check GoatFlow's) applies to
  the software. No license compatibility requirement is stated by TrueNAS.
- Community train apps are community-maintained; iXsystems does not support them.
  iXsystems support contract is for enterprise/stable trains only.
- Upstream image must be public/pullable by end users.
- Expectation: maintain your app — update `app_version`/`version` via PR when the
  upstream releases; a renovate bot tracks tags, and stale tags should be flagged
  by issue after 2 days.
- Deprecations: marked in-app for a 3-month period before removal.

## 8. Icons, screenshots, UI metadata

- Icon: PNG hosted at `https://media.sys.truenas.net/apps/<name>/icons/icon.png`.
  You provide the image in the PR description; the maintainer uploads it to the CDN
  and gives back the URL.
- Screenshots: same CDN pattern (`.../screenshots/screenshot1.png` etc.),
  referenced in `app.yaml` `screenshots`.
- `app_readme` HTML (shown in UI) is generated from `item.yaml`/`README.md`.
- Apps Market (apps.truenas.com) entries are generated from the catalog data;
  separate doc pages (InstallWizard*.md) live in the `truenas/apps-web` repo and
  are auto-populated — only contribute there for doc improvements.

## 9. Categories

Single `categories` entry in `app.yaml`. Observed categories across the catalog
(stable set): `media`, `monitoring`, `networking`, `productivity`,
`development`, `generic`, `utilities`, `security`, `databases`, `productivity`
variants like `productivity`, plus `tools`-style tags. Choose one best-fit
(GoatFlow → `productivity`). Categories drive the Discover-tab filters.

## 10. Submission / PR process

1. Check existing issues/PRs; open an issue or comment that you're working on it;
   a draft PR lets maintainers catch direction issues early.
2. Fork `truenas/apps`, add app under `ix-dev/community/goatflow/`.
3. Start from a similar existing app (copy + adapt).
4. Test locally: `./.github/scripts/ci.py --app goatflow --train community
   --test-file basic-values.yaml --wait=true` (or `devbox run app-test ...`).
   CI script auto-generates `item.yaml`, copies the library, renders, deploys,
   watches health (10-min timeout). Also: `generate_metadata.py` (capabilities),
   `port_validation.py`.
5. PR uses `.github/PULL_REQUEST_TEMPLATE/app_addition.md` — fill in description,
   upstream links (repo, docs, license, version), testing checklist, icons/
   screenshots (attach images; reviewer uploads to CDN and returns URLs).
6. GitHub Actions CI validates structure + runs test values; then a maintainer
   reviews; iterate; merge.
7. Post-merge: notify upstream (it's our own product, so this is internal),
   catalog updates daily on the Apps Market.

Help: https://github.com/truenas/apps/discussions, forums.truenas.com.

## 11. Alternative paths (non-store)

If we'd rather not depend on the official catalog:
- **Install via YAML**: users paste a Docker Compose YAML into Apps → Discover →
  ⋮ → "Install via YAML" (works on 24.10+).
- **Custom catalog**: users add our own git repo as a catalog (Discover → Manage
  Catalogs → Add Catalog, point at a GitHub repo structured like truenas/apps,
  or a simpler per-app structure — verify current repo layout docs when doing
  this; the catalog format for user-added repos is the same app-directory layout).
- **Portainer / Dockge**: both ship as standard apps for stack management.

## GoatFlow-specific notes / open items

- Confirm GoatFlow upstream license + public image registry (ghcr preferred) and
  that the image ships `curl` (or another binary) for the health check.
- Multi-service stack (Go + editor/attachments): model as multiple containers in
  one app, using `deps.postgres`/`deps.perms` patterns as applicable.
- Icon + 2–3 screenshots must be prepared before PR.
- `lib_version` must be re-checked at submission time (it moves).
- Decide: official community-train PR (recommended — store listing, auto-updates,
  zero user friction) vs our own custom catalog repo (faster iteration, users must
  add the catalog).
